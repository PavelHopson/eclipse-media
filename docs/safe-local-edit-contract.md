# Безопасный локальный монтаж: подготовленный контракт

Срез 28.08.2026. Утверждённый порядок: изоляция агентов → русская диктовка → монтаж.
Это **офлайн-контракт, интерактивный frontend-предпросмотр и тесты**, не готовый редактор:
HTTP endpoint, worker, FFmpeg, файловый доступ и публикация не добавлены. Экран «Безопасный
монтаж» демонстрирует точный путь решения, но честно заканчивается локальной квитанцией
предпросмотра и не заявляет, что итоговый файл создан.

## Что уже проверяется кодом

`backend/local_edit_contract.py` принимает один `eclipse.local-edit-plan.v1` до 16 КБ:

```json
{
  "schemaVersion": "eclipse.local-edit-plan.v1",
  "source": {
    "assetId": "00000000-0000-4000-8000-000000000005",
    "sha256": "aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa"
  },
  "trim": { "startMs": 1000, "endMs": 5000 },
  "outputProfile": "mp4-h264-aac-720p-v1"
}
```

Это искусственный пример, не хеш реального файла. Неизвестные/повторяющиеся поля запрещены.
Нет URL, путей, имени output, команд, фильтров или FFmpeg options от модели. Операция только одна:
вырезать интервал до 60 секунд из MP4 до 5 минут и 256 МБ. Фиксированный output profile задаёт
будущий encoder, но сейчас ничего не кодируется. Проверку реального контейнера/codec сделает worker.

`RunScope` и `SourceSnapshot` строит доверенный host, не клиент и не LLM. Источник связан с
workspace и владельцем; запуск — с user, employee, run и capability revision. Общий доступ
к чужому asset в первой версии не поддерживается. Snapshot должен отражать фактически прочитанный
локальный файл: этот модуль не проверяет диск и не может удостоверить достоверность metadata.

## Что теперь видно пользователю

В основной навигации Eclipse Media появился раздел «Безопасный монтаж»:

1. На одной сцене видны имя демо-источника, длительность и выбранный интервал.
2. Начало и конец меняются ползунками или точными числовыми полями. Ошибка диапазона
   блокирует подтверждение и объясняется рядом с границами.
3. До ручного подтверждения прав основная кнопка недоступна.
4. Раскрываемый блок показывает канонический JSON-план без URL, путей и команд.
5. После подтверждения интерфейс показывает digest, фиксированный профиль и ID квитанции,
   а также заметное состояние «Файл не создан».

Frontend использует ту же схему, профиль и ограничения длительности, что Python-контракт.
SHA-256 плана считается Web Crypto над канонической сериализацией. Это UX-регрессия и
визуальное доказательство потока, а не security boundary: доверенный host по-прежнему должен
повторно разобрать JSON и выдать одноразовое разрешение через `LocalExportGate`.

Проверено на 1440×1000 и 390×844, включая `prefers-reduced-motion: reduce`: горизонтального
переполнения нет, кнопка заблокирована до checkbox, а квитанция сообщает, что executor не запускался.

## Подтверждение и отмена

1. Host проверяет права пользователя и показывает точный read-only preview.
2. Отдельное ручное действие вызывает `approve()`. `approved_by` берётся из проверенной сессии;
   `rights_confirmed` — из доверенного UI решения, не из JSON плана. Этот boolean не доказывает
   права на контент и не заменяет аутентификацию, CSRF/IPC sender validation или проверку capability.
3. Выдаётся случайное разрешение на 120 секунд, привязанное к digest плана и snapshot исходника.
   Новое подтверждение заменяет старое. Токен не попадает в `repr`; его нельзя писать в логи/Chat.
4. `authorize()` атомарно поглощает разрешение один раз. Подмена интервала, asset, metadata,
   workspace/user/employee/run или revision отклоняется. Двойной клик не создаёт два разрешения.
5. Будущий worker повторно вызывает `assert_active()` с актуальными данными host перед завершением
   результата. `cancel()` и `revoke()` терминальны; после них требуется новый run.

Хранилище разрешений **in-memory, один процесс**. Несколько workers потребуют транзакционного
хранилища и проверки отзыва во время выполнения. Python-объект не является границей безопасности
против вредоносного кода в том же процессе. Проверка перед export сама по себе не закрывает TOCTOU.
Разрешение на монтаж не даёт прав публикации, облачной обработки или запуска shell.

## Тестирование

Из `backend`, в существующем Python 3.11+ окружении, без установки пакетов:

```powershell
python -m unittest test_local_edit_contract -v
```

19 проверок: строгая схема/размер, JSON duplicates и ошибки, числа, чужие источники и scope,
изменённый исходник/план, отсутствие прав, expiry, повтор, параллельный double-click, cancel/revoke
до и после authorize. Модуль использует только стандартную библиотеку. Тесты подхватываются
существующим CI через `python -m unittest -v`; полный локальный backend suite предыдущего
среза — 54/54.

Frontend дополнительно проверяет канонический план/digest, невозможность добавить команду,
неверный asset/hash, выход за source и предел 60 секунд через `npm test`; production-сборка
включает TypeScript-проверку.
Удалённый CI этим изменением не запускался.

## Что блокирует включение executor

- Реальный, явно выбранный тестовый MP4 с подтверждёнными правами.
- OS worker с запретом сети, read-only input, ограничениями CPU/времени/диска и дочерних процессов.
- Безопасное открытие и удержание file handle: traversal, symlink/junction и подмена после preview
  запрещены; output генерирует host внутри отдельного каталога, исходник не перезаписывается.
- Ограниченный media probe, обработка недоверенного файла, проверка выходного контейнера,
  длительности и воспроизведения; отдельный receipt только после успешного завершения.
- Cancel завершает всю группу процессов и очищает только временные файлы своего run.
- Привязка к действующей модели авторизации Chat/Sentinel и проверка отзыва после каждого await.
- Один реальный visual/audio smoke; исходный SHA неизменен, replay/ошибка не оставляют ready receipt.

До этих проверок статус — **contract-only**. Новых зависимостей, моделей, установок и production
изменений нет. Palmier остаётся архитектурным референсом; его код не импортирован.
