# Безопасный локальный монтаж: desktop runtime

Срез 30.08.2026. Утверждённый порядок: изоляция агентов → русская диктовка → монтаж.
Контракт подключён к **аутентифицированной desktop-сессии**, доверенному реестру завершённых MP4
и фиксированному FFmpeg worker. Публичный production остаётся в режиме preview-only: экспорт
нельзя включить без desktop session token, а Tauri sidecar выдаёт его только своему окну.
Публикации, загрузки в облако и произвольных команд в этом контуре нет.

## Что уже проверяется кодом

`backend/local_edit_contract.py` принимает один `eclipse.local-edit-plan.v1` до 16 КБ:

```json
{
  "schemaVersion": "eclipse.local-edit-plan.v1",
  "source": {
    "assetId": "00000000-0000-4000-8000-000000000005",
    "sha256": "aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa"
  },
  "trim": { "startMs": 1000, "endMs": 5000 },
  "outputProfile": "mp4-h264-aac-720p-v1"
}
```

Это искусственный пример, не хеш реального файла. Неизвестные/повторяющиеся поля запрещены.
Нет URL, путей, имени output, команд, фильтров или FFmpeg options от модели. Операция только одна:
вырезать интервал до 60 секунд из MP4 до 5 минут и 256 МБ. Фиксированный output profile реализован
как H.264/AAC MP4 1280×720. Worker повторно проверяет контейнер, codec, размер и длительность.

`RunScope` и `SourceSnapshot` строит доверенный host, не клиент и не LLM. Источник связан с
workspace и владельцем; запуск — с user, employee, run и capability revision. Общий доступ
к чужому asset в первой версии не поддерживается. Snapshot должен отражать фактически прочитанный
локальный файл. Runtime строит snapshot после копирования через открытый файловый дескриптор,
SHA-256 и ограниченный ffprobe; клиент не может передать путь.

## Что теперь видно пользователю

В основной навигации Eclipse Media появился раздел «Безопасный монтаж»:

1. Desktop автоматически предлагает завершённые MP4 из локальной очереди; браузер показывает
   только демонстрационный предпросмотр.
2. Начало и конец меняются ползунками или точными числовыми полями. Ошибка диапазона
   блокирует подтверждение и объясняется рядом с границами.
3. До ручного подтверждения прав основная кнопка недоступна.
4. Раскрываемый блок показывает канонический JSON-план без URL, путей и команд.
5. После подтверждения видны стадии проверки, кодирования и контроля результата; операцию можно
   отменить. Готовый файл получает SHA-256 и сохраняется через нативный Windows-диалог.

Frontend использует ту же схему, профиль и ограничения длительности, что Python-контракт.
Security boundary находится на host: JSON повторно разбирается, источник берётся из registry,
а одноразовое разрешение поглощается LocalExportGate. Токен разрешения живёт только между двумя
API-вызовами и не отображается.

## Подтверждение и отмена

1. Host проверяет права пользователя и показывает точный read-only preview.
2. Отдельное ручное действие вызывает `approve()`. `approved_by` берётся из проверенной сессии;
   `rights_confirmed` — из доверенного UI решения, не из JSON плана. Этот boolean не доказывает
   права на контент и не заменяет аутентификацию, CSRF/IPC sender validation или проверку capability.
3. Выдаётся случайное разрешение на 120 секунд, привязанное к digest плана и snapshot исходника.
   Новое подтверждение заменяет старое. Токен не попадает в `repr`; его нельзя писать в логи/Chat.
4. `authorize()` атомарно поглощает разрешение один раз. Подмена интервала, asset, metadata,
   workspace/user/employee/run или revision отклоняется. Двойной клик не создаёт два разрешения.
5. Worker повторно вызывает `assert_active()` с актуальными данными host перед завершением
   результата. `cancel()` и `revoke()` терминальны; после них требуется новый run.

Хранилище разрешений **in-memory, один процесс**, одновременно разрешён один экспорт.
Несколько workers потребуют транзакционного
хранилища и проверки отзыва во время выполнения. Python-объект не является границей безопасности
против вредоносного кода в том же процессе. Проверка перед export сама по себе не закрывает TOCTOU.
Разрешение на монтаж не даёт прав публикации, облачной обработки или запуска shell.

## Тестирование

Из `backend`, в существующем Python 3.11+ окружении, без установки пакетов:

```powershell
python -m unittest -v
```

61 backend-проверка, включая строгую схему/размер, JSON duplicates и ошибки, чужие источники и scope,
изменённый исходник/план, отсутствие прав, expiry, повтор, параллельный double-click, cancel/revoke
до и после authorize. Модуль использует только стандартную библиотеку. Тесты подхватываются
существующим CI через `python -m unittest -v`. Реальный smoke генерирует MP4 с видео и звуком,
выполняет trim, проверяет H.264 1280×720, неизменность исходника, one-time approval и отсутствие
путей/токенов в публичном статусе.

Frontend дополнительно проверяет канонический план/digest, невозможность добавить команду,
неверный asset/hash, выход за source и предел 60 секунд через `npm test`; production-сборка
включает TypeScript-проверку.
Frontend: 15/15 tests, TypeScript, ESLint и production build. Tauri: 3/3 Rust tests.

## Оставшиеся границы

- Это bounded trim, не универсальный видеоредактор и не агентский монтаж.
- FFmpeg получает только локальный staging-файл и protocol allowlist без HTTP(S), но дочерний процесс
  пока не помещён в отдельную OS sandbox/VM. Недоверенные codecs следует считать отдельным риском.
- Desktop требует локальные ffmpeg и ffprobe в PATH; installer их не загружает.
- Production containers получили read-only FS, limits и отдельную internal-сеть frontend. Backend
  сохраняет egress для yt-dlp; redirect-aware OS egress policy остаётся отдельным P1 gate.
- Полная привязка к Chat/Sentinel RBAC и durable audit появится только вместе с multi-user режимом.

Palmier остаётся архитектурным референсом; его код не импортирован.
